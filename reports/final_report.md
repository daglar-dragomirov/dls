# Итоговый отчет: Speech-Toolformer

## Задача

Реализован голосовой ассистент, который принимает текст или аудио, решает, нужен ли инструмент, формирует проверяемый JSON-вызов и исполняет функцию. Вместо погодного инструмента из примера выбраны две прикладные функции:

- `split_bill(amount, people, tip_percent, currency)` — расчет общей суммы и доли каждого участника;
- `convert_units(value, from_unit, to_unit)` — перевод длины, массы и температуры;
- `none()` — отрицательные примеры, где инструмент вызывать не следует.

## Датасет

С фиксированным seed сгенерированы 300 размеченных запросов с точным `expected_call`, включая разные формулировки, числа, валюты, единицы и класс `none`. Для каждого примера создан реальный TTS-аудиофайл; манифест связывает текст, путь и разметку.

Локальная open-weight модель `LiquidAI/LFM2.5-Audio-1.5B` официально ориентирована на английскую речь, поэтому основной GPU-бенчмарк использует все 82 доступных англоязычных примера после стратифицированной выборки по инструментам. Это не симуляция ASR: каждый MP3 действительно декодируется и проходит через модель на NVIDIA A40.

## Экспериментальные режимы

- **A, zero-shot:** аудио передается модели без описания допустимой JSON-схемы.
- **B, ASR:** аудио распознается локальной LFM2.5-Audio; считается WER.
- **C, direct:** аудио сразу преобразуется в JSON tool-call.
- **D, cascaded:** аудио → transcript → JSON tool-call.

Для C и D используется один и тот же системный контракт, few-shot примеры и строгий валидатор. Метрики считают невалидный ответ ошибкой: извлеченный из мусорного текста JSON не может искусственно повысить precision, recall или accuracy.

## Что дала настройка промпта

Без описания схемы модель не выдала ни одного валидного tool-call на 30 примерах. После добавления списка функций, строгого JSON-контракта, отрицательного класса и нескольких примеров direct-режим достиг parseability 1.0, F1 0.9286 и нулевого FAR. Это измеренная абляция, а не декларация о качестве промпта.

## Сравнение C и D

Direct pipeline выбран основным: он примерно в **2.04 раза быстрее** каскада, всегда возвращает валидную структуру и лучше по tool/argument accuracy. Cascaded pipeline сохранен в интерфейсе и API как диагностический режим: transcript помогает увидеть, где ошибка появилась в ASR, а где — в tool router.

## Анализ ошибок

1. **Валютные символы.** Фраза `dinner is 120 EUR` иногда распознается как `$120`; direct-модель ошибочно выбирает конвертацию валюты вместо `split_bill`.
2. **Непоследовательность tool name и arguments.** На `How many feet are in 3 meters` модель иногда пишет `tool_name: none`, но кладет правильные conversion-arguments. Строгий валидатор не засчитывает такой ответ.
3. **Числа и пунктуация повышают WER.** `$250` против `250 USD`, `six` против `6` и `10%` против `10 percent` лексически считаются ошибками, хотя смысл часто сохранен.
4. **Каскад накапливает ошибки.** Нормализация валюты или единиц в transcript меняет вход router, поэтому argument accuracy падает сильнее, чем в direct-режиме.

## Инженерная часть

- FastAPI-сервис с русскоязычным интерфейсом, загрузкой MP3/WAV/M4A и переключателем direct/cascaded;
- готовый тестовый MP3 по `/sample-audio`;
- строгая JSON-валидация, явные ошибки и отсутствие скрытого выполнения невалидных вызовов;
- CPU-friendly Railway-контур через OpenRouter и отдельный воспроизводимый GPU-контур;
- unit и integration tests, healthcheck, Docker/Railway-конфигурация;
- сохраненные сырые predictions и latency для независимой проверки.

## Вывод

Проект закрывает весь цикл Speech-Toolformer: дизайн датасета, zero-shot baseline, system-prompt tuning, реальный ASR-бенчмарк, прямой и каскадный audio pipeline, исполнение инструментов, метрики, анализ ошибок и развернутый сервис. Лучшим вариантом оказался direct audio-to-tool pipeline.
